# 34 — Authorization Checks

> **Lifecycle:** `CURRENT / RECOMMENDED`. `AUTHORITY-CHECK` works in Standard ABAP and in ABAP for Cloud Development; the cloud-specific parts are labelled where they appear. See [21-Classic-vs-Modern-ABAP](../21-Classic-vs-Modern-ABAP/README.md).

## 📖 Introduction

ABAP SQL on a database table checks no authorization. A program that reads or changes business data decides itself whether the current user may do so, and that decision is an `AUTHORITY-CHECK` whose result the program evaluates ([Rule 8.1](../docs/ABAP-Development-Rules.md#81-check-authorization-wherever-business-data-is-read-or-changed-and-evaluate-sy-subrc)).

The chapter covers:

- the authorization concept: objects, fields, activities, and roles and profiles as context;
- the statement `AUTHORITY-CHECK`, its return codes, `DUMMY` and `FOR USER`;
- where the check belongs, and how to put it behind an interface;
- testing the business logic with a double, and the check itself with SAP's ABAP Unit authorization test environment;
- finding out why a check failed;
- `SU24` proposals as context, and what applies in ABAP for Cloud Development.

Neighbouring topics are elsewhere: `CALL TRANSACTION ... WITH AUTHORITY-CHECK` in [14-Function-Modules](../14-Function-Modules/README.md), the `S_TABU_*` objects of table maintenance in [26-Maintenance-Views](../26-Maintenance-Views/README.md#-authorization-groups-and-authorization-objects), and checks in HTTP handlers in [25-HTTP-REST](../25-HTTP-REST/README.md#-security-in-handlers).

## 🔑 The Authorization Concept

According to the ABAP Keyword Documentation:

| Term | Meaning |
|---|---|
| **Authorization field** | The smallest unit: either data, such as a key of a table, or an activity, such as display or change. Maintained in `SU20`. |
| **Activity** | A two-character ID in the field `ACTVT`, for example `02` change and `03` display. SAP's activities are stored in table `TACT`, customer activities in `TACTZ`. |
| **Authorization object** | A repository object with up to ten authorization fields that are checked together. Grouped in object classes and maintained in `SU21`. |
| **Authorization** | Values or value ranges for the fields of one object: what a user may do with which data. |
| **Authorization profile** | A set of authorizations that is entered in the user master record. |
| **User master record** | The data of a user, including the profiles that the checks read. |

Authorizations and profiles are generated by role maintenance (`PFCG`) and assigned through roles. Role design, user administration and the generation of profiles are Basis work and outside this chapter. The Keyword Documentation names roles only in passing **[verify: SAP's definition of a role and how it generates profiles]**.

For a developer, the concept means two things: the program checks the right object with the right values, and someone else decides who holds which authorization. A program never checks a user name or a role name in place of an authorization.

## ✅ AUTHORITY-CHECK and sy-subrc

`AUTHORITY-CHECK OBJECT` names the object and, with `ID`, up to ten of its fields. Each field gets either `FIELD` with the value to check, or `DUMMY`. According to the ABAP Keyword Documentation, the check succeeds when the user master record holds at least one authorization for the object whose value sets contain every checked value. The result is in `sy-subrc`:

| `sy-subrc` | Meaning |
|---|---|
| 0 | Authorized, or no check took place (see below) |
| 4 | The user has authorizations for the object, but not for these values; also for an unknown field name or too many fields |
| 12 | The user has no authorization for the object at all |
| 24 | No longer set |
| 40 | `FOR USER` named an invalid user |

Only 0 means authorized. Evaluate it right after the statement and treat every other value as a refusal ([Rule 8.1](../docs/ABAP-Development-Rules.md#81-check-authorization-wherever-business-data-is-read-or-changed-and-evaluate-sy-subrc)).

Three details of the documentation matter in practice:

- **Unnamed fields and `DUMMY` are not checked.** Any value of the user's authorization is accepted for them. With `DUMMY` for every field, the check only asks whether the user has any authorization for the object. Use `DUMMY` only for a field that really does not matter, and say why ([Rule 8.18](../docs/ABAP-Development-Rules.md#818-use-dummy-only-for-a-field-that-does-not-matter-for-the-decision-and-say-why)).
- **No check, return code 0.** In the update task the statement checks nothing and sets 0. A check indicator that switches the object off for the current context, for example a transaction, also gives 0; the documentation notes that this is not possible for Basis and HR objects and recommends keeping checks on.
- **`FOR USER` checks another user.** The documentation warns that it can be misused to get around a check: never take the user name from outside the program.

> 📝 **Contextual snippet** — `table` holds the name of a table and `zcx_zsm_not_authorized` is the exception class of E2.

```abap
" Change access to one named table: both fields matter, so both are checked
AUTHORITY-CHECK OBJECT 'S_TABU_NAM'
  ID 'ACTVT' FIELD '02'
  ID 'TABLE' FIELD table.
IF sy-subrc <> 0.
  RAISE EXCEPTION NEW zcx_zsm_not_authorized( table = table ).
ENDIF.
```

> 💡 For reads in a loop over many rows, the Keyword Documentation names the class `CL_AUTH_OBJECTS_TO_SQL`, which turns a user's authorizations into a `WHERE` condition for ABAP SQL. It is not in SAP's release lists, so it is a Standard ABAP tool **[verify: CL_AUTH_OBJECTS_TO_SQL in your release]**.

### What the checks report

**Test record.** In the on-premise system used for this chapter, a probe class in `$TMP` called `AUTHORITY-CHECK` on `S_TABU_NAM` and never evaluated `sy-subrc`:

- The syntax check reported nothing, and the class activated.
- ATC with the system's default variant checked no object.
- ATC with the variant `DEFAULT` checked the class and reported no finding.
- ATC with the variant `SLIN_SEC` (Code Vulnerability Analyzer) checked no object.

None of the checks that ran found the unevaluated result. Whether the variants that ran include the extended program check is **[verify: the checks behind the variant DEFAULT, and the security checks of the extended program check and the Code Vulnerability Analyzer for an unevaluated sy-subrc]**. A review has to find this mistake; do not count on a tool.

## 🧱 Where the Check Belongs

The check belongs before the data is read or changed, in the layer that owns the access, so that every caller passes through it:

- **Entry points** check first: an RFC function module ([Rule 8.10](../docs/ABAP-Development-Rules.md#810-check-business-authorizations-at-every-rfc-entry-point)), an HTTP handler ([Rule 8.13](../docs/ABAP-Development-Rules.md#813-check-business-authorizations-in-every-http-handler-and-store-no-logon-data-in-a-service)), a report or a transaction.
- **Calling a transaction** uses `WITH AUTHORITY-CHECK`, which checks `S_TCODE` and raises `CX_SY_AUTHORIZATION_ERROR` ([Rule 8.9](../docs/ABAP-Development-Rules.md#89-call-transactions-with-authority-check), [14-Function-Modules](../14-Function-Modules/README.md)).
- **Generic table access** checks the table authorization ([Rule 8.14](../docs/ABAP-Development-Rules.md#814-assign-an-authorization-group-to-every-table-that-users-maintain-protect-sensitive-tables-additionally-with-s_tabu_nam), [11-Classical-Reports](../11-Classical-Reports/README.md), [26-Maintenance-Views](../26-Maintenance-Views/README.md#-authorization-groups-and-authorization-objects)).
- **The UI** may hide a button the user cannot use, but the check that protects the data sits below it.

Authorization objects are specific to an application. In the examples of this guide, a check with an object that the example is not about is replaced by a marker comment ([Rule 8.2](../docs/ABAP-Development-Rules.md#82-in-guide-examples-mark-where-the-check-belongs-never-invent-an-authorization-object)). The examples of this chapter are about table access, so they use the standard object `S_TABU_NAM` (fields `ACTVT` and `TABLE`).

## 🔌 The Check Behind an Interface

A business class that calls `AUTHORITY-CHECK` itself can be tested only with the authorizations of whoever runs the test. Behind an interface, the decision becomes a dependency that a test replaces ([Rule 8.17](../docs/ABAP-Development-Rules.md#817-put-authorization-checks-behind-an-interface-test-the-business-logic-with-a-double-and-the-check-with-the-abap-unit-authorization-test-environment), [Rule 5.4](../docs/ABAP-Development-Rules.md#54-depend-on-interfaces-and-receive-dependencies-through-the-constructor)).

**Example E1 — the authority interface and its implementation.** Target: Standard ABAP and ABAP for Cloud Development.

```abap
"! Decides whether the current user may display or change a table.
INTERFACE zif_zsm_table_authority
  PUBLIC.

  TYPES table_name TYPE c LENGTH 30.

  "! Whether the user may display the entries of a table.
  "! @parameter table  | Name of the database table
  "! @parameter result | abap_true if authorized
  METHODS may_display
    IMPORTING !table        TYPE table_name
    RETURNING VALUE(result) TYPE abap_bool.

  "! Whether the user may change the entries of a table.
  "! @parameter table  | Name of the database table
  "! @parameter result | abap_true if authorized
  METHODS may_change
    IMPORTING !table        TYPE table_name
    RETURNING VALUE(result) TYPE abap_bool.
ENDINTERFACE.
```

```abap
"! Table authorization through the standard object S_TABU_NAM.
CLASS zcl_zsm_table_authority DEFINITION
  PUBLIC
  FINAL
  CREATE PUBLIC.

  PUBLIC SECTION.
    INTERFACES zif_zsm_table_authority.

  PRIVATE SECTION.
    CONSTANTS:
      BEGIN OF activity,
        change  TYPE c LENGTH 2 VALUE '02',
        display TYPE c LENGTH 2 VALUE '03',
      END OF activity.

    METHODS is_authorized
      IMPORTING !table        TYPE zif_zsm_table_authority=>table_name
                activity_id   TYPE c
      RETURNING VALUE(result) TYPE abap_bool.
ENDCLASS.


CLASS zcl_zsm_table_authority IMPLEMENTATION.
  METHOD zif_zsm_table_authority~may_display.
    result = is_authorized( table = table activity_id = activity-display ).
  ENDMETHOD.

  METHOD zif_zsm_table_authority~may_change.
    result = is_authorized( table = table activity_id = activity-change ).
  ENDMETHOD.

  METHOD is_authorized.
    DATA(table_upper) = CONV zif_zsm_table_authority=>table_name( to_upper( table ) ).

    AUTHORITY-CHECK OBJECT 'S_TABU_NAM'
      ID 'ACTVT' FIELD activity_id
      ID 'TABLE' FIELD table_upper.

    " Only 0 means authorized; 4, 12 and every other value are refusals
    result = xsdbool( sy-subrc = 0 ).
  ENDMETHOD.
ENDCLASS.
```

**Example E2 — a business class that asks first.** Target: Standard ABAP and ABAP for Cloud Development. The class plans the export of a table and refuses before it reaches any data.

```abap
"! The current user is not authorized for the requested access.
CLASS zcx_zsm_not_authorized DEFINITION
  PUBLIC
  INHERITING FROM cx_static_check
  FINAL
  CREATE PUBLIC.

  PUBLIC SECTION.
    "! Name of the table the access was refused for
    DATA table TYPE zif_zsm_table_authority=>table_name READ-ONLY.

    METHODS constructor
      IMPORTING !table    TYPE zif_zsm_table_authority=>table_name OPTIONAL
                !previous LIKE previous OPTIONAL.
ENDCLASS.


CLASS zcx_zsm_not_authorized IMPLEMENTATION.
  METHOD constructor ##ADT_SUPPRESS_GENERATION.
    super->constructor( previous = previous ).
    me->table = table.
  ENDMETHOD.
ENDCLASS.
```

> 📝 ADT added the pragma `##ADT_SUPPRESS_GENERATION` to the constructor of the exception class on activation, in both systems; the source above is the active version.

```abap
"! Plans the export of a table; refuses before anything is read.
CLASS zcl_zsm_table_export DEFINITION
  PUBLIC
  FINAL
  CREATE PUBLIC.

  PUBLIC SECTION.
    "! @parameter authority | Decides whether the user may display a table
    METHODS constructor
      IMPORTING authority TYPE REF TO zif_zsm_table_authority.

    "! File name for the export of a table.
    "! @parameter table                  | Name of the database table
    "! @parameter result                 | File name in lower case
    "! @raising   zcx_zsm_not_authorized | The user may not display the table
    METHODS file_name_for
      IMPORTING !table        TYPE zif_zsm_table_authority=>table_name
      RETURNING VALUE(result) TYPE string
      RAISING   zcx_zsm_not_authorized.

  PRIVATE SECTION.
    DATA authority TYPE REF TO zif_zsm_table_authority.
ENDCLASS.


CLASS zcl_zsm_table_export IMPLEMENTATION.
  METHOD constructor.
    me->authority = authority.
  ENDMETHOD.

  METHOD file_name_for.
    " The check comes first, so a refused user never reaches the data
    IF authority->may_display( table ) = abap_false.
      RAISE EXCEPTION NEW zcx_zsm_not_authorized( table = table ).
    ENDIF.

    result = |{ to_lower( condense( table ) ) }.csv|.
  ENDMETHOD.
ENDCLASS.
```

The tests replace the authority with a double; no role and no authorization is needed:

```abap
"! Double for the authority: the business logic is tested without any role.
CLASS lth_authority DEFINITION FINAL FOR TESTING.
  PUBLIC SECTION.
    INTERFACES zif_zsm_table_authority.

    METHODS constructor
      IMPORTING allowed TYPE abap_bool.

  PRIVATE SECTION.
    DATA allowed TYPE abap_bool.
ENDCLASS.


CLASS lth_authority IMPLEMENTATION.
  METHOD constructor.
    me->allowed = allowed.
  ENDMETHOD.

  METHOD zif_zsm_table_authority~may_display.
    result = allowed.
  ENDMETHOD.

  METHOD zif_zsm_table_authority~may_change.
    result = allowed.
  ENDMETHOD.
ENDCLASS.


CLASS ltc_table_export DEFINITION FINAL FOR TESTING
  RISK LEVEL HARMLESS
  DURATION SHORT.

  PRIVATE SECTION.
    METHODS names_the_file_when_allowed FOR TESTING RAISING cx_static_check.
    METHODS refuses_when_not_allowed FOR TESTING.
ENDCLASS.


CLASS ltc_table_export IMPLEMENTATION.
  METHOD names_the_file_when_allowed.
    DATA(cut) = NEW zcl_zsm_table_export( NEW lth_authority( abap_true ) ).

    cl_abap_unit_assert=>assert_equals( act = cut->file_name_for( 'ZSM_T_ORDHDR' )
                                        exp = `zsm_t_ordhdr.csv` ).
  ENDMETHOD.

  METHOD refuses_when_not_allowed.
    DATA(cut) = NEW zcl_zsm_table_export( NEW lth_authority( abap_false ) ).

    TRY.
        cut->file_name_for( 'ZSM_T_ORDHDR' ).
        cl_abap_unit_assert=>fail( msg = 'A refused user must not get a file name' ).
      CATCH zcx_zsm_not_authorized INTO DATA(refusal).
        cl_abap_unit_assert=>assert_equals( act = refusal->table
                                            exp = 'ZSM_T_ORDHDR' ).
    ENDTRY.
  ENDMETHOD.
ENDCLASS.
```

## 🧪 Testing the Check Itself

The class that holds the `AUTHORITY-CHECK` needs a test of its own: does it check the right object with the right values, and does it treat a refusal as a refusal? SAP's release lists include an ABAP Unit test environment for this, `CL_AUNIT_AUTHORITY_CHECK` with the controller interface `IF_AUNIT_AUTH_CHECK_CONTROLLER`. According to its documentation:

- `create_auth_object_set` builds a set of authorizations: object, fields and value ranges, optionally for named users;
- the controller's `restrict_authorizations_to` limits the tester's authorizations to that set for the test session;
- `authorizations_expected_to` records which checks are expected to pass or fail, and `assert_expectations` fails the test when an expected check did not run or ended differently;
- `reset` undoes everything; call it in `teardown`.

> ⚠️ **The test environment restricts; it does not grant.** Its documentation says that only authorizations the tester really has can be kept. A test that needs an authorization the tester lacks is skipped, not passed. This was observed: in the SAP BTP ABAP environment the display test below was skipped, because the test user had no `S_TABU_NAM` authorization for the table; on-premise it ran and passed.

**Example E3 — the test include of E1.**

```abap
"! Tests the real check in the ABAP Unit authorization test environment.
"! The environment can only restrict the authorizations of the tester; it grants nothing.
CLASS ltc_table_authority DEFINITION FINAL FOR TESTING
  RISK LEVEL HARMLESS
  DURATION SHORT.

  PRIVATE SECTION.
    CONSTANTS order_table TYPE zif_zsm_table_authority=>table_name VALUE 'ZSM_T_ORDHDR'.

    DATA cut TYPE REF TO zif_zsm_table_authority.
    DATA controller TYPE REF TO if_aunit_auth_check_controller.

    METHODS setup.
    METHODS teardown.
    METHODS refuses_without_authorization FOR TESTING RAISING cx_static_check.
    METHODS display_only_allows_display FOR TESTING RAISING cx_static_check.

    METHODS display_authorization
      RETURNING VALUE(result) TYPE REF TO if_aunit_authority_objset.
ENDCLASS.


CLASS ltc_table_authority IMPLEMENTATION.
  METHOD setup.
    cut = NEW zcl_zsm_table_authority( ).
    controller = cl_aunit_authority_check=>get_controller( ).
  ENDMETHOD.

  METHOD teardown.
    controller->reset( ).
  ENDMETHOD.

  METHOD refuses_without_authorization.
    controller->restrict_authorizations_to( cl_aunit_authority_check=>create_auth_object_set( ) ).

    cl_abap_unit_assert=>assert_false( cut->may_display( order_table ) ).
  ENDMETHOD.

  METHOD display_only_allows_display.
    controller->restrict_authorizations_to( display_authorization( ) ).
    controller->authorizations_expected_to( pass_execution = display_authorization( ) ).

    cl_abap_unit_assert=>assert_true( cut->may_display( order_table ) ).
    cl_abap_unit_assert=>assert_false( cut->may_change( order_table ) ).

    controller->assert_expectations( ).
  ENDMETHOD.

  METHOD display_authorization.
    result = cl_aunit_authority_check=>create_auth_object_set(
        VALUE #( ( role_authorizations = VALUE #(
                     ( object         = 'S_TABU_NAM'
                       authorizations = VALUE #(
                         ( VALUE #( ( fieldname   = 'ACTVT'
                                      fieldvalues = VALUE #( ( lower_value = '03' ) ) )
                                    ( fieldname   = 'TABLE'
                                      fieldvalues = VALUE #( ( lower_value = order_table ) ) ) ) ) ) ) ) ) ) ).
  ENDMETHOD.
ENDCLASS.
```

> 📝 **Activation record.** E1, E2 and E3 were activated in both ABAP language versions: Standard ABAP and ABAP for Cloud Development. On-premise, all four test methods of E2 and E3 passed. In the SAP BTP ABAP environment, the two tests of E2 and `refuses_without_authorization` passed, and `display_only_allows_display` was skipped for the missing authorization described above. The active versions were read back and matched the sources. No user, role, profile or authorization was created or changed, and no table was read.

## 🔍 Tracing a Failed Check

When a user reports a missing authorization, find the check that failed before anyone changes a role:

| Tool | What it shows |
|---|---|
| `SU53` | The result of the last failed authorization check of a user; the ABAP Keyword Documentation names it for the last check results |
| `STAUTHTRACE` | The authorization trace, by its title in the system |
| `ST01` | The system trace, by its title in the system |
| `STSIMAUTHCHECK` | A simulation of authorization checks, by its title in the system |

All four exist in the on-premise system used for this chapter. What each shows in detail, and who may switch a trace on, is **[verify: SU53, STAUTHTRACE, ST01 and STSIMAUTHCHECK in your release]**. A trace records another user's activity: switch it on only for your own user, or with the user's consent and the Basis team's agreement, and switch it off afterwards. No trace was switched on for this chapter.

> 💡 A trace answers "which object and which values", which is what the role owner needs. "Give the user `SAP_ALL`" is not a fix; it is the end of the authorization concept.

## 🧭 SU24 Proposals and Roles (Context)

When a role is built in `PFCG` from transactions or services, the role tool proposes the authorization objects and values that those applications check. The proposals come from `SU22` for SAP's applications and from `SU24` for the customer's own maintenance; `SU24_S_TABU_NAM` exists for proposals of `S_TABU_NAM` **[verify: SU22, SU24 and how PFCG uses the proposals]**.

For a developer, this means: when your transaction or service checks an object, maintain the proposal in `SU24`, so that the role owner gets it. The roles themselves are Basis work.

## ☁️ Authorization in ABAP for Cloud Development

> **Lifecycle:** `ABAP CLOUD / MODERN CONTEXT`.

- **The statement works.** E1 activated in ABAP for Cloud Development with `AUTHORITY-CHECK` on `S_TABU_NAM`, which SAP's release lists include together with its fields `ACTVT` and `TABLE`. Use released objects or objects of your own software component ([Rule 1.2](../docs/ABAP-Development-Rules.md#12-when-targeting-abap-for-cloud-development-use-only-released-apis)).
- **Own authorization objects** are repository objects in ADT. In the SAP BTP ABAP environment used for this chapter, `S_TABU_NAM` exists as an authorization object and as an object of type `SIA3`, and IAM apps (`SIA6`) were offered as creatable objects. How own objects, IAM apps, business catalogs and business roles fit together is **[verify: the IAM model for custom authorization objects in the SAP BTP ABAP environment]**.
- **CDS access control** restricts which rows a CDS entity returns, with access conditions and PFCG conditions; `WITH PRIVILEGED ACCESS` switches it off ([Rule 8.3](../docs/ABAP-Development-Rules.md#83-use-with-privileged-access-only-with-a-written-justification)). It belongs to [CDSGuide](https://github.com/serhatmercan/CDSGuide).
- **RAP authorization** checks in the behavior of a business object; the Keyword Documentation names the RAP-specific variant `AUTHORITY-CHECK DISABLE`. It belongs to the future RAPGuide.
- **Business roles and catalogs** in the Fiori launchpad belong to UIGuide.

## ✅ Best Practices

- Check before reading or changing, in the layer that owns the data, and evaluate `sy-subrc` — [Rule 8.1](../docs/ABAP-Development-Rules.md#81-check-authorization-wherever-business-data-is-read-or-changed-and-evaluate-sy-subrc).
- Treat every return code except 0 as a refusal.
- Name every field that matters; use `DUMMY` only with a reason — [Rule 8.18](../docs/ABAP-Development-Rules.md#818-use-dummy-only-for-a-field-that-does-not-matter-for-the-decision-and-say-why).
- Put the check behind an interface; test the business logic with a double and the check with `CL_AUNIT_AUTHORITY_CHECK` — [Rule 8.17](../docs/ABAP-Development-Rules.md#817-put-authorization-checks-behind-an-interface-test-the-business-logic-with-a-double-and-the-check-with-the-abap-unit-authorization-test-environment).
- Maintain `SU24` proposals for the objects your application checks.
- Find a failed check with `SU53` or a trace before a role is changed.

## ⚠️ Common Mistakes

- An `AUTHORITY-CHECK` whose `sy-subrc` is never read; no check that ran for this chapter reported it.
- Treating 4 as "no authorization object" and 12 as "no values", or only one of them as a refusal.
- `DUMMY` for a field whose value was simply not at hand.
- `FOR USER` with a name taken from input.
- Checking a user name or a role name instead of an authorization.
- A check only in the UI, so that an RFC or HTTP caller bypasses it.
- Inventing an authorization object in an example or a specification.
- Tests that pass only for developers with broad authorizations.
